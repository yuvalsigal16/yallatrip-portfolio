# שלב 4: התחברות

## מה בנינו

| יכולת | איך זה עובד |
| --- | --- |
| הרשמה עם אימייל וסיסמה | שם, אימייל, סיסמה ואימות. נשלח מייל אישור, והלחיצה עליו מחברת ומעבירה ל-Onboarding |
| התחברות והרשמה עם Google | כפתור אחד. Google מחזיר את המשתמש אלינו, ואם זו הפעם הראשונה נוצר לו חשבון |
| שכחתי סיסמה | שולחים קישור למייל. הקישור מחבר ופותח את מסך "סיסמה חדשה" |
| Onboarding | שלוש שאלות: סגנון טיול, תקציב, תחבורה. אפשר לדלג. התשובות נשמרות כברירת מחדל לכל טיול חדש |
| דפים מוגנים | "הטיולים שלי" ו"פרופיל" רק למחוברים. מי שלא מחובר מועבר להתחברות, ואחריה חוזר בדיוק לאן שרצה |
| פרופיל | עריכת שם, יציאה, ומחיקת חשבון (עם אישור בהקלדת "מחיקה") |

## למה ככה

| החלטה | למה |
| --- | --- |
| Supabase Auth, לא מערכת משלנו | סיסמאות מוצפנות, מיילים, Google, הגבלת ניסיונות וחידוש session מוכנים ובדוקים. מערכת התחברות היא לא מקום לחסוך |
| שני שומרים: proxy וגם כל דף | ה-proxy (לשעבר middleware) מפנה מהר, אבל כל דף מוגן בודק את המשתמש בעצמו. גם אם אחד מהם ייפול, השני יעצור |
| הודעות שגיאה עמומות בכוונה | "האימייל או הסיסמה לא נכונים", ו"אם יש חשבון, שלחנו קישור". כך אי אפשר לברר דרך הטפסים אילו אימיילים רשומים |
| הגנה מ-Open Redirect | הכתובת "לאן לחזור אחרי ההתחברות" מתקבלת רק אם היא בתוך האתר. `//evil.com` ודומיו נחסמים (יש לזה בדיקות) |
| מחיקת חשבון בפונקציה בבסיס הנתונים | המשתמש מוחק רק את עצמו, בלי שנצטרך לשמור מפתח מנהל בשרת. המחיקה מוחקת בשרשרת גם את כל הטיולים |
| סיסמה: 8 תווים, אותיות וספרות | איזון בין אבטחה לנוחות. Supabase בודק שוב גם בצד שלו |
| טפסים שעובדים גם בלי JavaScript | Server Actions: הטופס נשלח גם אם הסקריפט עוד לא נטען. בזמן השליחה הכפתור ננעל |

## הגדרות חד-פעמיות (בלוחות הבקרה, לא בקוד)

**ב-Supabase → Authentication → URL Configuration**
- Site URL: ‏`http://localhost:3000` (ובהמשך כתובת האתר האמיתית)
- Redirect URLs: להוסיף `http://localhost:3000/auth/callback` (ובהמשך `https://הדומיין-שלך/auth/callback`)

**התחברות עם Google**
1. ב-Google Cloud Console → APIs & Services → Credentials → Create OAuth client ID → Web application.
2. ב-Authorized redirect URIs מדביקים את הכתובת שמופיעה ב-Supabase תחת Authentication → Providers → Google (נראית כמו `https://xxxx.supabase.co/auth/v1/callback`).
3. את ה-Client ID וה-Client Secret מדביקים ב-Supabase באותו מסך ומפעילים את Google.
4. ב-OAuth consent screen: שם האפליקציה GoTrip, ואימייל לתמיכה.

**מיילים**
- השרת המובנה של Supabase מגביל את כמות המיילים לשעה ומתאים רק לבדיקות. לפני השקה מחברים SMTP (למשל Resend) תחת Authentication → Emails → SMTP Settings.
- אפשר לתרגם לעברית את תבניות המיילים באותו מסך.

**ידנית, בדפדפן** (אחרי `npm run dev`)
1. פותחים http://localhost:3000/trips בלי להיות מחוברים → מועברים ל-`/login?next=/trips`.
2. נרשמים עם אימייל → מופיעה הודעת "שלחנו מייל אישור". לוחצים על הקישור במייל → מגיעים לשלוש השאלות.
3. עונים או מדלגים → מגיעים ל"הטיולים שלי" עם השם שלך.
4. יוצאים ומתחברים שוב → מגיעים ישר ל"הטיולים שלי", בלי השאלות.
5. מנסים סיסמה שגויה → "האימייל או הסיסמה לא נכונים".
6. "שכחתי סיסמה" → מייל → קישור → סיסמה חדשה → "הסיסמה עודכנה".
7. "התחברות עם Google" → בוחרים חשבון → חוזרים מחוברים.
8. כשמחוברים, פותחים `/login` → מועברים ל"הטיולים שלי".
9. בפרופיל: משנים שם. מוחקים את החשבון → חוזרים לדף הבית עם "החשבון נמחק". ב-Supabase → Authentication → Users המשתמש כבר לא קיים.

**מה לא נבדק אצלי:** את הזרימה בדפדפן מול Supabase ו-Google אמיתיים לא יכולתי להריץ, כי אין לי גישה ל-npm ולחשבונות. בדקתי את הלוגיקה, את בסיס הנתונים ואת הטיפוסים.
